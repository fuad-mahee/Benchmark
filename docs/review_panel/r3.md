# Artefact-Evaluation Review — `docs/benchmark_study.tex`

## (a) Overall assessment

The study's core empirical work is unusually well-evidenced: I independently re-derived the RQ1 census, the anchoring result, the full RQ1 factorial, and every number in the RQ2 detection table from the stored artefacts, and they match exactly — the factorial decomposition (+1 / +14 / +1,549) reproduces to the token from three archived generation files, and the anchor (2,537 of GlitchCleaner's 2,539, Jaccard 0.993344) is exact against `third_party/GlitchCleaner/Glitchtokens/Mistral-7B-Instruct-v0.1-glitch-tokens.csv`. Against that, three problems are serious: the RQ3 argument that "the reported gain is not attainable" rests entirely on a grid the study itself labels as produced by a known error, and is directly contradicted by the study's own corrected artefact; a leakage figure is stated twice as "18 of 197" when every stored artefact says 10 of 197; and three of the four advertised reproducibility properties (traceability, checkpoint guards, externalised configuration) are not implemented as described for the artefacts that back the headline tables. Appendix A also does not match the repository — several listed paths do not exist, one row points at an artefact that was never produced, and the document's single most-cited table has no script and no output file. The repository was additionally not quiescent during review: `eval.json`, `split.json`, `train_meta.json`, `adapter/`, and `alpha_beta_grid.csv` were all overwritten in place between 00:47 and 00:53, destroying at least one artefact the document cites.

## (b) Required changes, most important first

**1. §RQ3 lines 765–777 — the central RQ3 argument is built on data the study has superseded, and is contradicted by its own corrected result.**
The document states (lines 771–773) "at the paper's own fixed values we obtain a repair rate *higher* than the $12.92\%$ it reports for that configuration," then concludes "some $(\alpha,\beta)$ would have to deliver roughly $60\%$ repair. The maximum anywhere in our grid is $24.0\%$." Both figures (20.8% at (4,1.5); 24.0% max) come only from `results/gp_repair/mistral-7b-instruct-v01/alpha_beta_grid.v1_product_last.csv`, which the document itself identifies as the product-stream/all-positions configuration produced by error E1. The study's *corrected* artefact, `results/gp_repair/mistral-7b-instruct-v01/summary.json` (`stream_mode: "separate"`, `position: "token"`, paper protocol, same held-out half), gives `rule_based.repair_rate = 0.06477` — **6.48%, which is lower than 12.92%**, inverting the premise. The corrected grid that began writing during this review (`alpha_beta_grid.csv`) is consistent with this: α=1 row tops out at 2.6% and α=2 at 4.6%, versus 6.8% and 16.0% in the v1 grid. *Required:* either delete this paragraph until the corrected grid completes, or restate it against the corrected numbers and say explicitly that 6.48% at (4, 1.5) is *below* the paper's 12.92% baseline. As written the document asserts an empirical claim its own repository refutes.

**2. §4.4 line 356 and §5.3 D5 line 466 — the held-out leakage count is wrong.**
Both places state "$18$ of $197$ nominally held-out tokens." The stored artefacts say 10: `results/gc/mistral-7b-instruct-v01/split.json` has `"heldout_dropped_leaked"` of length 10 and `"heldout_ids_before_leak_filter"` of length 197 (leaving 187), and `train_meta.json` records `"n_heldout_dropped_leaked": 10`, `"n_heldout": 187`. I searched every version of `split.json` in git history (`706e27d`, `36a3094`, `0c03490`, `a3d1042`, `HEAD`) — none contains 18. `docs/RUNLOG.md` repeats the same "18/197". *Required:* change both occurrences to 10 of 197 (or produce the artefact that yields 18), and fix RUNLOG.

**3. §4.7 lines 388–394 — the traceability claim is false for the artefacts backing Tables 1, 2 and 3.**
The document says "Every result file records timestamp, git commit, *whether the working tree was modified at the time*, and the versions of PyTorch, Transformers, PEFT and scikit-learn." Only 6 of the 25 result JSONs contain `git_dirty` and `env`. The four files that back the two census columns and both detection rows —
`results/ground_truth/mistral-7b-instruct-v01/summary.json`, `.../gccode/summary.json`, `results/gp_detect/mistral-7b-instruct-v01/summary.json`, `.../gccode/summary.json` — carry only `timestamp` and `git_commit`. `results/benchmark_report.json` carries neither. The census summary is attributed to commit `c269d8f` ("Checkpoint/resume infrastructure…"), one commit *before* `e4006f3` ("RQ1 Mistral census + gccode protocol variant") — i.e. precisely the dirty-tree case the paragraph says the flag was added to expose, and it is still unrecorded. *Required:* either re-run the census and detection under the current `run_metadata()` (which does emit `git_dirty` and `env`), or weaken the claim to "every result file produced after commit `0c03490`," and add a table listing which artefacts predate the change.

**4. `results/gp_repair/mistral-7b-instruct-v01/alpha_beta_grid_meta.json` — post-correction metadata is attached to pre-correction results, which is the exact failure §4.7 claims was eliminated.**
The file at HEAD reads `"timestamp": "2026-07-30T18:39:13"`, `"git_commit": "0c03490"`, `"git_dirty": true`, `"stream_mode": "separate"`, `"position": "token"` — yet its `"best_cell": {"alpha": 16.0, "beta": 0.5, "repair_rate": 0.24, "normal_break_rate": 0.018}` is byte-identical to the best cell of the *v1 product/last* grid, and no `alpha_beta_grid.csv` existed alongside it. Git confirms the mechanism: at `5d9188c` and `0c03490` the meta was the pre-audit one (timestamp `2026-07-19T16:30:11`); at `a3d1042` the CSV was renamed to `.v1_product_last.csv` and the meta was replaced with a fresh-metadata/stale-result file. The v1 CSV also has only 4 columns while the current `grid_sweep()` writes 8, proving the current code never produced it. *Required:* delete or rename `alpha_beta_grid_meta.json` to `alpha_beta_grid_meta.v1_product_last.json` and strip the `stream_mode`/`position`/`best_cell` fields it cannot support; the file as it stands would mislead any independent reader exactly as §4.7 warns.

**5. §4.7 lines 397–402 — the checkpoint-guard claim covers one code path, not "long sweeps."**
"Long sweeps checkpoint per batch and resume exactly. Resumption is guarded by a configuration fingerprint." `checkpoint_guard` is referenced from exactly one place — `src/glitchprober/sweep_alpha_beta.py:25–35` (cell-level, α/β grid only). The *per-batch* path the sentence describes is `repetition_sweep` in `src/ground_truth/sweep.py:54–60`, which drives the census, both detection sweeps, and every repair evaluation:

```python
if checkpoint.exists():
    results = _load_checkpoint(checkpoint)
    todo = [t for t in token_ids if t not in results]
```

No fingerprint, no config comparison — it will silently extend any checkpoint it finds. This is not hypothetical: `results/ground_truth/.../gccode/budget24/sweep_checkpoint.csv`, a factorial cell, is written by this unguarded path. *Required:* either extend `checkpoint_guard` to `repetition_sweep`, or restate as "the α/β grid's cell-level checkpoint is guarded by a configuration fingerprint; the per-batch sweep checkpoints are not."

**6. §RQ1 lines 583–585 — the newline comparison uses a different predicate on each side.**
"$1{,}088$ of $31{,}743$ generations ($3.4\%$) consist of newlines only, against $3$ under \Ppaper{}". Recomputing from the archived generations: under $P_{\mathrm{code}}$, 1,088 outputs are newlines-only (verified); under $P_{\mathrm{paper}}$ the count of newline-only outputs is **0**. The value 3 is the count of whitespace-only-or-empty outputs (2 non-empty whitespace + 1 empty). *Required:* either "1,088 newline-only against 0" or "1,089 whitespace-only against 3" — as written the two sides are not the same measurement.

**9. §RQ2 lines 651–662 — the kernel attribution is well-supported as an observation but has no control artefact.**
The measurements verify exactly: text divergence 0.368% ($P_{\mathrm{paper}}$) and 0.420% ($P_{\mathrm{code}}$) — matching the stated "0.37–0.42%" as protocol-level totals — and verdict divergence 2 of 9,522 = 0.021% under both. The systematicity claim is genuinely strong: on tokens sampled by more than one seed, divergence is perfectly reproducible (2/2, 3/3, 1/1 overlap, zero eager-vs-eager text mismatches). But the *causal* attribution to the attention kernel is inference from the fact that two different scripts used different kernels — I had to confirm it from git (`git show e4006f3:scripts/run_ground_truth.py` → `load_model(mcfg, attn_impl=None)`; `git show 32ba28a:scripts/run_gp_detect.py` → `attn_impl="eager"`). No A/B run exists. *Required:* run the census once with `--attn-impl eager` and report the direct contrast, or state "the two scripts differ only in attention kernel; we did not run the controlled A/B."

**10. §RQ3 lines 779–783 — the $m$-sweep sentence is incomplete and one-sided, and its artefact has no provenance.**

**12. §7.2 line 853 — "$3{,}504$ have a stripped length of at most one character" is wrong.**

The difference is exactly the 31 whitespace-only tokens named in the preceding clause, so "at most one" double-counts them. *Required:* "and a further $3{,}504$ have a stripped length of exactly one character."
